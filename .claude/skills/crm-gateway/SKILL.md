# CRM gateway: the live Salesforce CRM

The real CRM is reached only through the **CSCSW GW Prod** connector. It exposes
governed agents, not tables. You never write SOQL or SQL, and raw records never
enter the model's context. Every call runs **as the signed-in user**, with their
Salesforce access and their persona (for example `sales_rep`).

## Two business lines: always keep them separate
The CRM holds **Laundry** (Account record type **Route**, branches in `Branch__c`) and **Air**
(record type **Air**, regions in `Air_Area_Branch__c`). They have different branch networks and
very different revenue per account (about $900 vs about $350 a month). Report them side by side,
never blended. `Line_of_Business__c` is blank, so split on record type. See `crm-revenue-by-branch`
for field details.

## Which agent to call

| Need | Tool | Example query (pass the user's words verbatim) |
|---|---|---|
| Analytics across accounts: rankings, revenue, "top N", owners | `ask` | `top 20 accounts by revenue` |
| One named account: briefing, "what's going on with X", record lookup | `coworker_search` | `brief me on PURDUE UNIVERSITY` |
| The signed-in rep's own deals and pipeline health | `pipeline_my` | `what's my pipeline health score`, `Show my open opportunities`, `How reliable is my forecast?` |

Rules:
- **Pass the request through verbatim.** Don't paraphrase or pre-summarize. A follow-up
  ("only the worst 5") goes to the **same** tool as the request it refines.
- **Stay inside the role.** `pipeline_my` is the rep's own pipeline, not a team or org view.
  A tool outside the role is refused; say so rather than working around it.
- **Phrasing:** avoid "sum", "grouped", "rollup" and "metadata". The router sends them to a warehouse that isn't connected. Use "show … by …". For field metadata, use `coworker_search`: "find the record for X and list its <topic> fields with API names and values".
- **Writes are proposals.** Some suggested next steps ("Clean up my past-due opps") would
  change records. The gateway returns a proposal that needs explicit confirmation. Never
  confirm one yourself, and never put a write in a dashboard.

## The answer card

Every tool returns JSON like this:

```json
{ "title": "Ask · Salesforce CRM", "runs_as": "<viewer>", "persona": "sales_rep",
  "ask": "<the query>", "answer": "<markdown>", "records": [],
  "next_steps": [{"label": "...", "query": "..."}],
  "instance_url": "https://cscsw.my.salesforce.com", "live": true, "has_card": true }
```

- **The data is in `answer`, as Markdown.** Tables are Markdown tables. Record links are
  relative (`/lightning/r/Account/<id>/view`): prefix `instance_url`. `records` is empty today.
- **The wording is generated by an agent, so layout can drift** (column names, headings).
  Parse defensively: take the first table, find columns by pattern (`/account|name/i`,
  `/amount|value/i`, `/close/i`), and treat a missing table as "no data", not an error.
- **Briefings contain contact emails and phone numbers.** Strip them before showing
  a briefing to anyone else (see `data-dashboard-builder` for the scrubber).

## Using it in a Claude Data dashboard

A dataset is one gateway call:

```json
{ "kind": "call", "connector": "CSCSW GW Prod", "tool": "ask",
  "args": { "query": "top {{n}} accounts by revenue" },
  "rules": { "n": { "enum": [10, 20, 50] } } }
```

- Give every `{{blank}}` a tight rule. Account names use
  `^[\p{L}\p{M}\p{N} .,&/#()-]{1,80}$`, with no quotes.
- Add a `dash.loader` that parses the card. Tested loaders for tables, briefings,
  health scores and forecast ratings are in
  `.claude/skills/data-dashboard-builder/kit/build_crm.py`.
- Because every call runs as the viewer, **each person sees their own CRM**. That's
  the point for `pipeline_my`. Say so on the page.

## Recommendation for the gateway team

Dashboards would be sturdier if the gateway filled `records` with the rows behind each
table (for example `[{account, account_id, avg_monthly_revenue, ...}]`). Then no
Markdown parsing would be needed and the numbers could be certified.
